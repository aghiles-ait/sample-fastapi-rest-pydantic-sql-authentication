# Sample FastAPI REST API — Books & Authentication

A minimal REST API built with [FastAPI](https://fastapi.tiangolo.com/) that manages a collection of books and their readers, persisted in a [SQLite](https://www.sqlite.org/) database via [SQLAlchemy](https://www.sqlalchemy.org/) (2.0 style). It's a learning project covering routing, path & query parameters, request validation and response serialization with [Pydantic](https://docs.pydantic.dev/), ORM persistence, password hashing and JWT authentication, all in a layered project structure (routes / schemas / repositories / models / database).

## Requirements

- Python 3.10+
- [FastAPI](https://fastapi.tiangolo.com/) and an ASGI server ([Uvicorn](https://www.uvicorn.org/))
- [SQLAlchemy](https://www.sqlalchemy.org/) 2.0+
- [bcrypt](https://github.com/pyca/bcrypt) — password hashing
- [PyJWT](https://pyjwt.readthedocs.io/) — JWT signing and verification
- [pydantic-settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/) — `.env` loading
- SQLite — bundled with Python (no server to install)

## Installation

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env            # then put a real key in JWT_SECRET_KEY
python -c "import secrets; print(secrets.token_hex(32))"
```

The app reads `JWT_SECRET_KEY` at import time and **refuses to start without it** — see
[Configuration](#configuration).

> **Watch your interpreter.** If `uvicorn` resolves to a Python other than the venv's, you
> get `ModuleNotFoundError` on `bcrypt` or `jwt` even though `pip install` succeeded. Check
> with `which -a uvicorn`, or start the app with `python -m` to make the interpreter
> explicit: `./venv/bin/python -m uvicorn main:app --reload --port 8080`.

## Running the app

```bash
uvicorn main:app --reload --port 8080
```

The API is then available at `http://localhost:8080`.

- Interactive docs (Swagger UI): `http://localhost:8080/docs`
- Alternative docs (ReDoc): `http://localhost:8080/redoc`

The SQLite database file (`base.db`) is created automatically on startup: the app's
`lifespan` handler calls `Base.metadata.create_all(...)` before serving the first request.

## Endpoints

| Method | Path                | Description                                              | Auth | Success code |
|--------|---------------------|---------------------------------------------------------|------|--------------|
| GET    | `/`                 | Health check / hello message                            | —    | 200          |
| POST   | `/register`         | Register a new user (`username` + `password`)           | —    | 201          |
| POST   | `/login`            | Exchange credentials for a JWT access token             | —    | 200          |
| GET    | `/me`               | Current user, decoded from the `Bearer` token           | **Bearer** | 200    |
| GET    | `/books`            | List books, with optional `category` / `rating` / `year` filters | — | 200 |
| GET    | `/books/{book_id}`  | Get a single book by its id (`book_id > 0`)             | —    | 200          |
| POST   | `/books`            | Create a book (id is generated by the database)         | —    | 201          |
| PUT    | `/books/{book_id}`  | Full replacement of a book (all fields required)        | —    | 204          |
| PATCH  | `/books/{book_id}`  | Partial update (only provided fields are changed)       | —    | 204          |
| DELETE | `/books/{book_id}`  | Delete a book                                           | —    | 204          |

A missing `book_id` returns `404`; invalid input (e.g. `rating` out of range, `book_id <= 0`) returns `422`.

> **The `/books` routes are not protected yet.** Authentication exists end to end
> (`/register` → `/login` → `Bearer` token → `get_current_user`), but only `/me` consumes it.
> See [Protecting a route](#protecting-a-route).

### Query filters on `GET /books`

All three are optional and can be combined:

- `category` — exact match (e.g. `science`, `history`, `math`)
- `rating` — integer between 0 and 5
- `year` — publication year (1000–2026)

## Data model

Three tables: `books`, `users`, and `loans` linking them.

```
users ──< loans >── books
```

A user can borrow several books and a book can be borrowed by several users — a many-to-many
relationship, which needs its own table. `Loan` is a full model rather than a plain
association table because a loan has attributes of its own (`borrowed_at`, `due_date`,
`returned_at`), and because `returned_at IS NULL` is what distinguishes an ongoing loan from
a past one. Its primary key is a standalone `id`, not the `(user_id, book_id)` pair: the same
user may borrow the same book again later, and a composite key would overwrite that history.

> **`loans` is mapped but not exposed.** The table is created at startup; no endpoint reads
> or writes it yet. Copies are not tracked either — nothing currently prevents two concurrent
> loans of the same book. The rule "one active loan per book" would be a
> `select(Loan).where(Loan.book_id == x, Loan.returned_at.is_(None))` check before insert.

### Book

A book is exposed by the API with the following shape:

```json
{
  "id": 1,
  "title": "A Brief History of Time",
  "author": "Stephen Hawking",
  "category": "science",
  "rating": 5,
  "published_year": 1988
}
```

Validation rules (on create/update):

- `title` — min length 3
- `author` — min length 1
- `category` — min length 3
- `rating` — integer, 0–5
- `published_year` — integer, 1000–2026

> **Note:** data is persisted in the `base.db` SQLite file, so it survives server
> restarts. `id` is auto-incremented by the database, so it must **not** be sent in the
> request body.

### Examples

```bash
# All books
curl http://localhost:8080/books

# Filter by category and rating
curl "http://localhost:8080/books?category=science&rating=5"

# Get one book by id
curl http://localhost:8080/books/1

# Create a book
curl -X POST http://localhost:8080/books \
  -H "Content-Type: application/json" \
  -d '{"title":"Cosmos","author":"Carl Sagan","category":"science","rating":5,"published_year":1980}'

# Partial update
curl -X PATCH http://localhost:8080/books/1 \
  -H "Content-Type: application/json" \
  -d '{"rating":4}'

# Delete
curl -X DELETE http://localhost:8080/books/1
```

## Users & registration

`POST /register` creates a user and returns it without any credential:

```bash
curl -X POST http://localhost:8080/register \
  -H "Content-Type: application/json" \
  -d '{"username":"aghiles","password":"a-strong-password"}'
```

```json
{ "id": 1, "username": "aghiles", "is_active": true, "role": "user" }
```

Validation rules:

- `username` — 3 to 50 characters, unique across users
- `password` — 8 to 72 characters (bcrypt only reads the first 72 bytes)

A username already taken returns `409`; invalid input returns `422`.

Two deliberate omissions in the schemas:

- `role` is **not** accepted in the request body, otherwise anyone could register as an
  admin. It keeps its `"user"` default and is only changeable server-side.
- `hashed_password` is **not** part of `UserResponse`, so it can never leak into a response.

The password is never stored in clear text: `security.hash_password` runs bcrypt with a
per-user salt embedded in the resulting hash, which is why registering the same password
twice produces two different hashes. Verification re-runs the hash instead of decrypting
anything.

## Login & JWT

`POST /login` exchanges credentials for a signed token:

```bash
curl -X POST http://localhost:8080/login \
  -H "Content-Type: application/json" \
  -d '{"username":"aghiles","password":"a-strong-password"}'
```

```json
{ "access_token": "eyJhbGciOiJIUzI1NiIs...", "token_type": "bearer" }
```

The token carries `sub` (username), `id`, `role` and `exp`. It is **signed, not encrypted**:
anyone holding it can read its payload (try it on [jwt.io](https://jwt.io/)), but the HMAC
signature makes it impossible to alter without the secret key. Never put anything
confidential in it.

Three details in `/login` are deliberate:

- Wrong password and unknown username return the **same** `401` with the same message, so the
  API can't be used to enumerate accounts.
- When the username doesn't exist, a dummy bcrypt hash is verified anyway
  (`security.DUMMY_PASSWORD_HASH`). Without it the response returns instantly instead of
  ~240 ms, and a stopwatch is enough to tell existing accounts apart.
- `is_active` is checked **after** the password, not before — otherwise a `403` would reveal
  that the account exists to someone who doesn't know its password.

### Using the token

```bash
curl http://localhost:8080/me -H "Authorization: Bearer $TOKEN"
```

```json
{ "id": 1, "username": "aghiles", "role": "user" }
```

In Swagger UI: `POST /login`, copy `access_token`, click **Authorize** at the top right,
paste it. The padlock then applies to every protected route.

`GET /me` is the visible face of `routers.auth.get_current_user`, the dependency that reads
the `Authorization: Bearer …` header, verifies the signature and expiry, and returns a
`CurrentUser`. Every failure mode answers `401` with a `WWW-Authenticate: Bearer` header:
missing header, wrong scheme, altered signature, expired token, token signed with another
key, or a payload missing a field.

`HTTPBearer` is used rather than `OAuth2PasswordBearer` because `/login` takes a JSON body,
not an OAuth2 form. It is declared with `auto_error=False`: left to itself, FastAPI answers
`403` when the header is absent, whereas missing authentication is a `401`.

> **`get_current_user` reads the token only — it never queries the database.** No SELECT per
> request, but a deactivated account stays valid until its token expires (up to 30 minutes).
> Add a `get_user_by_username` call inside the dependency if you need immediate revocation.

### Protecting a route

The dependency exists and is ready to use. To require a valid token on the whole `/books`
router:

```python
# routers/books.py
router = APIRouter(prefix="/books", tags=["books"],
                   dependencies=[Depends(get_current_user)])
```

Or per route, when the handler needs to know *who* is calling:

```python
def create_book(..., current_user: Annotated[CurrentUser, Depends(get_current_user)]):
```

The `role` claim is already in the token, so a `require_admin` dependency built on top of
`get_current_user` could keep `GET /books` open to any authenticated user while reserving
`POST` and `DELETE` for admins.

### Configuration

Settings are read from a `.env` file at the project root (see `.env.example`):

| Variable | Default | Description |
|---|---|---|
| `JWT_SECRET_KEY` | *(required)* | HMAC signing key — the app refuses to start without it |
| `JWT_ALGORITHM` | `HS256` | Signature algorithm |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Token lifetime |

Generate a key with:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

`JWT_SECRET_KEY` has no default on purpose: a key hardcoded in the source would end up
published with the repository, and anyone could then forge a valid token. `.env` is
git-ignored.

## Project structure

```
.
├── main.py             # FastAPI app: lifespan + router registration (entry point)
├── routers/            # HTTP layer, one module per resource
│   ├── books.py        #   /books endpoints
│   └── auth.py         #   /register, /login, /me + get_current_user dependency
├── schemas/            # Pydantic request validation + response DTOs
│   ├── book.py         #   BookPostPutRequest, BookPatchRequest, BookResponse
│   └── user.py         #   RegisterRequest, LoginRequest, TokenResponse,
│                       #   UserResponse, CurrentUser
├── repositories/       # Data-access functions (SQLAlchemy queries), one module per table
│   ├── book.py
│   └── user.py
├── models.py           # SQLAlchemy ORM models (User, Book, Loan)
├── database.py         # Engine, SessionLocal factory, declarative Base, get_db dependency
├── security.py         # Password hashing (bcrypt) + JWT creation/decoding
├── config.py           # Settings read from .env (pydantic-settings)
├── .env                # Secrets — git-ignored, see .env.example
├── .env.example        # Template to copy
├── base.db             # SQLite database file (created at runtime)
└── README.md
```

The layers are kept separate on purpose:

- **app** (`main.py`) owns only the `FastAPI` instance, the `lifespan` handler that creates
  the tables, and the `include_router(...)` calls. It holds no business logic, which is what
  lets any router import the database session without a circular import.
- **routes** (`routers/`) handle HTTP: they parse requests, inject a database session via
  the `get_db` dependency, translate outcomes into status codes (`404`, `409`, `422`, `201`…),
  and serialize responses through `response_model`. One module per resource.
- **schemas** (`schemas/`) validate input and shape output. Input schemas
  (`BookPostPutRequest`, `RegisterRequest`) and output DTOs (`BookResponse`, `UserResponse`)
  are kept distinct from the ORM models, so the API contract and the database schema can
  evolve independently — and so a field like `hashed_password` never leaks into a response.
- **repositories** (`repositories/`) own all data access. They receive the session and run
  the SQLAlchemy queries (`select`, `db.get`, `add`/`commit`/`refresh`, `delete`), rolling
  back on write failures. They never raise HTTP errors — that's the routes' job. One module
  per table, so the auth code doesn't drag the whole book CRUD along with it.
- **models** (`models.py`) are the ORM entities mapped to the `users`, `books` and `loans`
  tables.
- **database** (`database.py`) wires up the engine, the session factory, the declarative
  base and the `get_db` dependency — the single place a session is opened and closed.
- **security** (`security.py`) isolates password hashing and JWT creation, so no other module
  ever handles a plaintext password or depends directly on bcrypt / PyJWT.
- **config** (`config.py`) reads the settings from `.env` once, at import time, so no secret
  is ever hardcoded or read from `os.environ` scattered across the code.

Two rules keep the layering honest:

- A router never builds an ORM object. `routers/` passes plain values and the repository
  instantiates the entity, so adding a column touches the data layer only — `models` is not
  imported anywhere under `routers/`.
- A repository never raises `HTTPException`. It reports failure (`SQLAlchemyError`,
  `IntegrityError`) and the route decides the status code. That's what keeps the repositories
  usable from a script, a scheduled job or a test.

Because persistence goes through SQLAlchemy, switching to another database (e.g. PostgreSQL)
mostly comes down to changing the connection URL in `database.py` and installing a driver —
the models, repositories and routes stay the same.

## Known gaps

Deliberate shortcuts, listed so they're choices rather than oversights:

- **No service layer.** Business logic lives in the routes (the "username already taken"
  check, the password hashing call). Fine while one route means one operation. Creating a
  loan will break that: it needs to check the book, check the user, insert, and commit as a
  single transaction across two repositories. That's when `services/` becomes worth adding —
  and when `commit()` should move out of the repositories, which currently own the
  transaction boundary themselves.
- **No migrations.** `Base.metadata.create_all()` creates missing tables but never runs
  `ALTER TABLE`, so changing an existing model leaves the database behind — a column added to
  `User` will surface as `no such column` at runtime, not at startup. Dropping `base.db` is
  enough for now; [Alembic](https://alembic.sqlalchemy.org/) is the real answer.
- **`/books` is unauthenticated**, as noted above.
- **No `/logout`.** A JWT is stateless: it stays valid until `exp`, and there is nothing
  server-side to invalidate. Real logout needs either a short expiry plus refresh tokens, or
  a revocation list.
- **No tests in the repository.** The flows have been exercised manually through
  `fastapi.testclient.TestClient`, but nothing is committed.
